# 写作框架

## 1. 题干覆盖表

先把题干转换为下表，不要只按论文标题自由发挥：

| 题干要求 | 计划落点 | 素材状态 |
|----------|----------|----------|
| 项目与个人职责 | 摘要、项目背景 | 已确认 / 缺失 |
| 理论、方法或阶段 | 理论说明 | 已确认 / 待核验 |
| 项目实践或问题解决 | 实践分论点 | 已确认 / 缺失 |
| 效果、问题或总结 | 分论点结尾、全文结尾 | 已确认 / 缺失 |

题干有几个问题，覆盖表就保留几个独立落点。生成提纲和完稿检查时逐项回查。

## 2. 项目素材底稿

按以下字段整理事实，不要求一次填满：

- 时间与周期：何时启动、实施多久、何时上线；
- 背景与用户：为何建设、服务谁、解决什么问题；
- 范围与功能：核心模块、系统边界和关键规模；
- 个人角色：职位、决策职责和实际完成的工作；
- 技术决策：候选方案、约束、选型依据；
- 实施证据：具体步骤、参与者、组件、模型或配置；
- 结果证据：测试、运行数据、业务反馈；
- 问题复盘：实际不足、原因和改进动作。

用 `已确认`、`合理推导`、`缺失` 标记每项。禁止将范文中的项目事实迁移给用户。

## 3. 五部分结构

### 摘要

按“项目背景与功能 + 个人角色 + 核心论点 + 项目结果”组织。摘要不是引言，避免只讲行业背景。正文的每个核心分论点应在摘要有对应概括。

### 项目背景

围绕 Why、Who、What、When、How 选择必要信息：需求来源、使用者、核心功能、时间周期、个人职责和与主题相关的技术约束。避免罗列与论题无关的全部模块。

### 理论说明

直接回答题干中的概念、特点、候选方法、阶段或质量属性。先给定义或总述，再列出题干需要的内容，最后用过渡句引向项目实践。

### 实践论证

先总述项目采用的核心方案，再按题干和项目事实拆成若干分论点。每段使用：

`目标或问题 → 选型依据 → 实施过程 → 技术细节 → 风险处理 → 效果证据`

不是每段都要机械写满六项，但至少包含项目动作和结果，不能只列技术名称。

### 结尾

依次写项目结果、与主题相关的不足、对应改进措施和个人总结。避免用“得到一致好评”“继续努力学习”代替证据与复盘。

## 4. 动态篇幅

先执行考试界面或完整题干明确给出的硬限制。没有硬限制时，可以将下列比例作为规划起点，而非官方标准：

- 摘要：全文的约 10%～12%；
- 项目背景：约 15%～18%；
- 理论说明：约 15%～18%；
- 实践论证：约 40%～50%；
- 结尾：约 15%～18%。

部分备考资料建议摘要约 280～320 字、全文约 2500～2700 字。这些范围相互并不完全一致，只能在没有硬约束时用于估算。实践分问题通常应获得最多篇幅。

## 5. 输出模板

### 教练模式当前阶段

1. 审题结果或当前段落诊断；
2. 已确认素材；
3. 缺失或冲突信息；
4. 下一步只询问最关键的一项。

### 直接模式事实不足

使用醒目的事实占位符，例如：

- `【项目上线时间】`
- `【个人实际职责】`
- `【故障恢复指标】`
- `【压测或运行结果】`

不要用看似真实的随机数字替代占位符。
