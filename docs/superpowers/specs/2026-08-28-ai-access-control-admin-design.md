# AI 助手后台访问控制设计

## 背景

生产 AI 助手当前使用 `AI_ROLLOUT_ALLOWED_USER_IDS` 环境变量维护普通用户内测名单，管理员角色默认开放。调整名单需要登录服务器、修改环境文件并重建 AI 容器，无法由后台管理员自助操作，也缺少全局紧急关闭入口和持久化审计。

本设计把访问控制迁移到 MySQL，在现有后台提供全局一键开关和内测名单管理。修改即时影响后续请求，不再依赖重启容器。

## 目标与非目标

### 目标

- 管理员可以在后台一键关闭或开启 AI 助手。
- 管理员可以从 AI 设置页和用户管理页维护同一份内测名单。
- 权限修改即时生效，并记录修改人和修改时间。
- 保留管理员默认开放、考试期间禁用及每日 Token 额度控制。
- 数据库或配置读取异常时默认拒绝 AI 请求，避免意外扩大开放范围。

### 非目标

- 本期不实现灰度分组、开放比例、预约生效时间或名单有效期。
- 本期不改变用户角色、考试状态或 Token 额度的业务规则。
- 本期不取消已发往模型供应商的调用。
- 本期不把访问控制字段加入 Java `user` 表。

## 已确认的产品规则

- 全局开关关闭时，包括管理员在内的所有用户均不可使用 AI 助手。
- 全局开关开启时，管理员和内测名单中的有效用户可以使用。
- 用户处于考试模式时，即使具有访问资格也临时禁用 AI 助手。
- 全局开关关闭后仍允许管理员编辑内测名单，但后台必须提示名单暂不生效。
- 普通用户可从用户管理页直接切换“AI 内测”，也可从 AI 设置页集中添加或移除；两个入口操作同一份数据。
- 管理员显示为“管理员默认开放”，不需要加入名单，也不能通过名单开关取消其管理员默认权限。
- 上线完成后的默认生产状态为“全局开启，仅管理员和内测名单开放”。

## 方案比较

### 方案一：AI 服务持久化独立访问配置（采用）

在 AI 服务已有的 Alembic/SQLAlchemy 持久化层增加全局配置和内测名单表，由 AI 服务负责管理员接口和运行时授权。该方案不需要重启容器，边界与现有 AI 额度配置一致，并可独立扩展审计字段。

### 方案二：在 `user` 表增加 `ai_enabled`

实现直观，但把 AI 发布策略耦合到核心用户模型；全局开关、修改审计以及未来的分组或有效期会继续膨胀主用户表，因此不采用。

### 方案三：继续使用环境变量

改动最少，但无法满足后台即时控制、双入口同步和审计要求，因此仅作为一次性迁移输入，不再作为长期运行时配置。

## 权限模型与优先级

每个 AI 业务请求都在服务端重新判断访问资格，不能依赖前端隐藏按钮。

判断顺序固定为：

1. 读取全局配置；若关闭，返回 `AI_GLOBALLY_DISABLED`。
2. 判断用户角色或内测名单；非管理员且不在有效名单中，返回 `AI_ROLLOUT_NOT_ENABLED`。
3. 通过 Java 平台内部接口检查考试状态；考试中返回 `AI_DISABLED_DURING_EXAM`。
4. 继续执行既有每日 Token 额度、并发和 Run 约束。

数据库不可用、配置表存在但单例行缺失、平台考试状态检查失败时均 fail closed，不调用模型。单例只允许由 Alembic 创建；生产运行时不得自动补建或恢复默认开启。仅测试夹具或显式的管理员修复命令可以重建。管理员身份只能绕过名单检查，不能绕过全局开关、考试限制或额度控制。

## 数据模型

使用 Alembic 新增以下表。

### `ai_access_config`

单例配置表：

- `id`：固定为 `1`，主键。
- `globally_enabled`：非空布尔值，默认 `true`。
- `updated_by_user_id`：最近操作的管理员用户 ID，可空，仅初始化时为空。
- `create_time`、`update_time`：服务端时间。

迁移创建默认行 `id=1, globally_enabled=true`。更新时锁定单例行，并在事务提交后才向 API 返回成功。

### `ai_rollout_users`

普通用户内测名单：

- `user_id`：主键，引用的是平台 `user.id`，不创建跨服务外键。
- `created_by_user_id`、`updated_by_user_id`：操作管理员 ID。
- `create_time`、`update_time`。

表中存在记录即表示用户位于名单中。`PUT` 使用幂等 upsert；重复添加不会产生多条记录。`DELETE` 采用物理删除以保持名单查询简单，操作写入下述持久化审计表和结构化日志。名单记录数、列表和批量状态都只以记录是否存在为准。若未来需要软停用，再单独增加状态字段，不在本期扩大范围。

### `ai_access_audit_log`

持久化访问控制变更历史：

- `id`：自增主键。
- `action`：`GLOBAL_ENABLE`、`GLOBAL_DISABLE`、`ROLLOUT_ADD` 或 `ROLLOUT_REMOVE`。
- `admin_user_id`：操作管理员 ID。
- `target_user_id`：名单操作目标；全局开关操作为空。
- `old_value`、`new_value`：变更前后布尔值。
- `create_time`：操作时间。

配置或名单变更与对应审计记录在同一个数据库事务中提交；审计写入失败则整个修改失败。结构化应用日志仍用于监控，但数据库审计表是后台操作历史的权威来源。

## 服务边界与数据流

访问控制由 `aisoftoj-ai` 所有，沿用其现有数据库会话、管理员 JWT 验证和异常响应机制。

AI 设置页的数据流：

1. 前端读取全局配置和按 `user_id` 排序的名单分页结果。名单分页不接受关键词，以 AI 数据库记录分页，确保 `total` 准确；当前页最多 100 个 ID，再批量向 Java 补齐展示信息。
2. “搜索添加”是独立候选用户搜索：AI 服务携带管理员 Bearer JWT 调用 Java `GET /admin/users`，按用户名、邮箱或 ID 获取平台用户分页；前端结合 AI 批量名单状态标记“已添加/可添加”。移除已有用户可直接从名单当前页操作，或在用户管理页搜索后操作。
3. 添加前，AI 服务调用新增 Java `POST /internal/ai/admin/users:batch-get` 验证目标用户存在、未删除且已启用。请求同时携带 `X-AI-Service-Key` 与原管理员 Bearer JWT；Java 先校验 Service Key，再校验 Bearer JWT 的管理员角色。
4. AI 服务在事务中写入名单，并返回最终状态。
5. 前端重新读取服务端结果，不依赖本地猜测。

用户管理页的数据流：

1. 继续由 Java 后台返回用户分页。
2. 前端将当前页普通用户 ID 批量发送给 AI 管理接口。
3. AI 管理接口返回每个 ID 的名单状态；前端合并展示“AI 内测”列。
4. 切换开关时调用与 AI 设置页相同的 `PUT` 或 `DELETE` 接口。

批量查询避免逐用户请求和 N+1 问题。全局配置和名单每个权限请求直接读取数据库；首版不引入进程内缓存，保证修改即时生效并避免多副本缓存一致性。若观测到明显数据库压力，再增加带主动失效的短 TTL 缓存。

新增 Java 批量用户接口的请求为 `{"user_ids":[17,23]}`，最多接受 100 个去重后的正整数。响应保持请求顺序，每项只包含 `id`、`login_name`、`nick_name`、`email`、规范化 `role`、`is_enabled`、`is_deleted`；该接口不对公网暴露，由现有 Nginx 规则继续阻止 `/internal/*`。不存在的 ID 以 `missing_user_ids` 单独返回，这属于合法完整响应，不等同于结构缺项。AI 服务调用超时或响应结构不合法时整体返回 503：添加操作不写数据库，名单分页不返回不完整结果。

名单记录不使用跨服务外键。用户在加入后若被禁用、软删除或物理删除，其 JWT 验证会阻止新请求；名单页仍返回该记录，并根据 Java 结果标记 `account_status=disabled|deleted|missing`，允许管理员移除。此类 tombstone 不自动清理，避免无审计的隐式写入。“名单记录数”按 AI 表记录计数，不声称是当前有效用户数；运行时有效资格始终要求通过平台 JWT 用户校验且名单记录存在。相关账号恢复启用后，原名单记录重新生效。

## API 设计

所有 `/api/ai/admin/*` 接口要求 `ADMIN` 角色。

### 全局配置

- `GET /api/ai/admin/access-config`
  - 返回 `globally_enabled`、`updated_by_user_id`、`updated_at` 和名单记录数。
- `PATCH /api/ai/admin/access-config`
  - 请求：`{"globally_enabled": false}`。
  - 仅接受布尔值；幂等设置相同值仍返回当前最终状态。

### 内测名单

- `GET /api/ai/admin/rollout-users?page=1&page_size=20`
  - `page_size` 范围为 1–100，不接受关键词；按 `user_id` 稳定排序后分页。
  - 返回 `{records,total,page,page_size}`；记录包含 `user_id`、`login_name`、`nick_name`、`email`、`role`、`account_status`、`created_by_user_id`、`updated_by_user_id`、`created_at`、`updated_at`。缺失账号的展示字段为空但名单记录仍返回。
- `POST /api/ai/admin/rollout-user-status:batch-get`
  - 请求：`{"user_ids": [2, 17, 23]}`，限制最多 100 个唯一正整数。
  - 返回 `{"globally_enabled":true,"statuses":{"2":false,"17":true,"23":false}}`；只返回请求中的 ID，名单不存在时为 `false`，不要求平台用户再次存在性校验。
- `PUT /api/ai/admin/rollout-users/{user_id}`
  - 验证目标用户是存在且启用的普通用户后幂等加入名单。
- `DELETE /api/ai/admin/rollout-users/{user_id}`
  - 幂等移除；目标不在名单中也返回成功后的禁用状态。

目标用户不存在或已删除时，`PUT` 返回 `404 AI_ROLLOUT_USER_NOT_FOUND`；用户已禁用时返回 `409 AI_ROLLOUT_USER_DISABLED`；目标是管理员时返回 `409 AI_ROLLOUT_ADMIN_IMPLICIT_ACCESS`；平台校验不可用时返回 `503 AI_PLATFORM_UNAVAILABLE`。数据库访问失败统一返回 `503 AI_ACCESS_CONFIG_UNAVAILABLE`。

现有 `GET /api/ai/capability` 是特殊的“必须认证、只评估、不强制拒绝”端点。它复用与业务路由完全相同的访问决策服务，但把正常的允许/拒绝决策映射为 HTTP 200；未登录仍返回 401，数据库或 Java 依赖故障仍返回对应 503。其他 AI 业务路由把同一拒绝决策强制映射为 403。capability 新增/沿用以下结果：

- `{"ai_enabled": false, "reason": "AI_GLOBALLY_DISABLED"}`
- `{"ai_enabled": false, "reason": "AI_ROLLOUT_NOT_ENABLED"}`
- `{"ai_enabled": false, "reason": "AI_DISABLED_DURING_EXAM"}`
- `{"ai_enabled": true, "reason": null}`

AI 业务接口继续用 403 表示可预期的访问拒绝；配置或平台依赖不可用时返回 503，不伪装成无权限。

## 后台交互

### AI 助手设置页

在现有每日 Token 额度卡片前增加“AI 功能开关”卡片：

- 显示当前“已开启/已关闭”、影响说明、最近修改时间和管理员 ID。
- 关闭使用危险色按钮并弹出二次确认，文案明确“所有用户（包括管理员）将无法发起新的 AI 请求”。
- 开启无需二次确认，成功后显示“仅管理员和内测名单可用”。
- 保存中禁用重复操作；失败时恢复服务端真实状态并显示错误。

同页增加“内测人员”区域：

- 展示名单记录数、搜索框、候选用户和已开通列表。
- 支持按用户名、邮箱或用户 ID 搜索、添加和移除。
- 全局关闭时显示提示“总开关已关闭，名单可编辑但暂不生效”。
- 管理员搜索结果标记“管理员默认开放”，不展示添加按钮。

### 用户管理页

- 表格增加“AI 内测”列。
- 普通用户使用原生可访问开关；管理员显示“管理员默认开放”。
- 被禁用或已删除用户不能打开 AI 内测开关。
- 当前页名单状态加载失败时显示“状态未知”和重试入口，不能默认显示关闭后允许覆盖。
- 修改失败时开关恢复服务端状态，并在行内显示错误。

## 运行中请求与即时生效

关闭全局开关或移除用户时，不取消已经发往模型供应商的调用，允许该次调用完成并按真实 usage 正常结算 Token。访问检查同时挂载在 Run 创建入口和模型适配器每轮调用之前；下一轮检查失败后不再调用工具或模型。

在多轮 Run 中途失去访问权限时，Run 终态固定为 `failed`，`error_code` 写入当次稳定原因码 `AI_GLOBALLY_DISABLED` 或 `AI_ROLLOUT_NOT_ENABLED`，通过既有 `run.failed` 事件结束 SSE。已经完成并落库的消息保留；正在流式生成但尚未形成完整 assistant 消息的部分内容不落库，用户输入消息保留。客户端刷新后应看到 Run 失败而不是 completed/cancelled，并可在权限恢复后重新发起请求。

已打开 AI 面板的用户无需重新登录；下一次 capability 刷新或业务请求会获得新状态。前端收到访问拒绝后关闭输入能力并展示对应中文提示。后台修改成功后不要求部署或重启服务。

## 迁移与上线

1. 发布前读取并备份旧 `AI_ROLLOUT_ALLOWED_USER_IDS` 精确值到 root-only、带发布版本号的回滚环境文件；生产 `ai.env` 在整个回滚观察期保持原值。
2. 在旧应用仍服务流量时运行 Alembic，创建两张表和默认全局配置行；旧应用继续只读取环境变量，不受新表影响。
3. 在新服务对外切换前运行一次性迁移命令：严格解析并去重旧 ID，调用 Java 批量用户接口验证目标，管理员 ID明确跳过，不存在、已删除或已禁用 ID 写入迁移报告但不导入。旧名单为空时跳过 Java 调用，不需要管理员令牌；非空时命令必须通过 `--admin-token-file` 接收一个短期管理员 JWT 文件，并从现有 root-only `ai.env` 读取 Service Key。令牌文件由发布操作者临时创建为 root:root、`0600`，命令先调用管理员校验接口确认未过期且角色为 ADMIN；完成或失败后均立即安全删除。令牌值不得出现在命令行参数值、环境变量、迁移报告或日志中。
4. 迁移命令在单个数据库事务中幂等导入所有有效普通用户；提交后重新读取并比较有效 ID 集合和数量。解析失败、临时令牌缺失/过期/非管理员、Java 校验不可用、数据库失败或集合不一致均阻止上线。
5. 切换到新应用。新版本仅在访问控制表“不存在”这一特定 MySQL 错误下兼容读取旧变量；表存在但连接失败、权限不足、超时或单例行缺失时一律 fail closed，禁止回退环境变量。
6. 完成生产权限矩阵验证后进入一个发布观察期。观察期内不删除旧变量和版本化回滚文件；新版本因表存在而忽略它们。
7. 下一版本结束观察期后，删除旧变量、回滚备份、兼容读取代码和对应配置字段。

回滚旧应用时，先从版本化回滚文件原子恢复旧 `ai.env`，再启动旧镜像，并复核容器内名单值和 capability。新增表在回滚时保留，不执行破坏性降级。

## 安全、异常与审计

- 管理接口复用当前 JWT 验证，并在服务端强制检查大写规范化后的 `ADMIN` 角色。
- 前端展示不是安全边界；所有 AI 业务路由统一调用同一个访问控制服务。
- 添加名单前验证目标用户存在、未删除且启用；无效目标返回 404 或 409，不写数据库。
- 数据库写入使用事务、唯一约束和确定的锁顺序。
- 结构化日志记录管理员 ID、目标用户 ID、旧状态、新状态和请求结果，不记录 JWT、Service Key、用户消息或 LLM Key。
- 配置读取失败返回 `503 AI_ACCESS_CONFIG_UNAVAILABLE`；写入失败不改变前端显示的最终状态。
- 生产运行时发现 `ai_access_config` 表存在但 `id=1` 缺失时必须返回 503，不得自动插入 `globally_enabled=true`。
- 增加全局开关修改、名单添加/移除、权限拒绝及配置读取失败指标。

## 测试与验收

### 服务端

- 覆盖全局开/关、管理员/名单用户/普通用户、考试中/非考试中的完整权限矩阵。
- 验证管理员不能绕过全局关闭、考试限制或 Token 额度。
- 验证非管理员不能调用管理接口。
- 覆盖 Alembic 创建配置单例、幂等开关、名单重复添加、重复移除和并发写入。
- 覆盖不存在、已删除、被禁用及管理员目标用户。
- 覆盖数据库不可用和平台用户校验不可用时 fail closed。
- 覆盖 capability 未登录为 401、正常拒绝为 200、依赖故障为 503，并断言它与业务路由使用同一优先级决策。
- 覆盖配置表存在但单例行缺失时 fail closed 且不产生自动插入。
- 覆盖名单用户后续被禁用、删除或查询不到时无法使用 AI，名单页返回可移除 tombstone，账号恢复后的既定重新生效语义。
- 覆盖环境变量名单一次性迁移和旧版本回滚兼容。
- 覆盖非空旧名单迁移时临时管理员令牌缺失、过期、角色不符和清理，断言均阻止上线且日志不包含令牌。
- 覆盖开关、名单添加和名单移除与审计记录同事务提交，并验证审计失败时业务修改回滚。
- 覆盖多轮 Run 在两次模型调用之间关闭全局开关或移除用户，断言 Run 为 `failed`、稳定错误码、`run.failed`、无后续工具/模型调用及正确额度结算。

### 前端

- AI 设置页覆盖开关加载、关闭确认、开启、失败恢复、名单搜索、添加和移除。
- 用户管理页覆盖批量状态合并、普通用户切换、管理员标签、禁用用户和加载失败。
- 两个入口修改后重新读取同一服务端状态，验证状态同步。
- capability 原因码映射为明确中文提示，不展示原始内部错误码。

### 生产 E2E

1. 使用管理员账号关闭全局开关，验证管理员与内测用户均无法发起新 Run。
2. 重新开启，验证管理员可用。
3. 添加一个普通测试用户，刷新页面后验证其 AI 面板和 Run 正常。
4. 移除该用户，验证下一次请求被拒绝。
5. 验证未加入名单的普通用户始终不可用。
6. 验证考试中的管理员或内测用户仍不可用。
7. 最终恢复“全局开启，仅管理员和内测名单开放”，并确认健康检查、日志和指标正常。
8. 从 AI 设置页添加用户后在用户管理页确认开启，再从用户管理页移除并回到 AI 设置页确认消失。
9. 在测试 Run 的首轮模型调用结束后关闭总开关，验证下一轮不再调用模型、SSE 收到 `run.failed` 且用量正确。
10. 演练数据库/Java 校验依赖不可用时 fail closed，并执行一次旧版本回滚环境文件恢复的无流量演练。

## 验收标准

- 管理员无需 SSH、修改环境变量或重启容器即可维护 AI 开关和内测名单。
- 后台两个入口展示并修改同一份状态。
- 全局关闭可以可靠阻止所有新 AI 请求，重新开启后只开放管理员和名单用户。
- 权限规则在前端、capability 和所有 AI 业务接口上保持一致。
- 迁移不扩大现有生产开放范围，并具备可执行的旧版本回滚路径。
