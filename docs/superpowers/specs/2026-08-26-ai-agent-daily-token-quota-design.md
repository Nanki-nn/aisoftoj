# AI 助手 Agent 每日 Token 额度设计

## 目标与范围

为线上 AI 助手 Agent 增加按用户独立计算、但额度标准相同的每日 Token 额度：每名用户默认每天 30,000 Token。管理员可在后台统一修改所有用户的额度标准，修改立即生效。额度按北京时间（Asia/Shanghai）每天 00:00 自然切换。

本设计只覆盖 AI 助手 Agent，不覆盖已废弃的论文批改功能。论文批改相关代码、接口和历史数据本期不删除、不改造，仅在项目文档中标记为“已废弃，不计入 AI 助手额度”。

线上 AI 面板不常驻展示用户剩余额度，避免增加使用负担；额度用尽时才显示中性提示并禁用发送。

## 已确认的产品规则

- 每名普通用户独立拥有每日额度，所有用户使用同一个全局额度标准，初始值为每人 30,000；用户之间不共享或争抢额度池。
- 管理员可在后台修改额度，立即影响新发起的 Run 和后续模型调用。
- 已消耗 Token 不因调额回滚；调低到已用量以下时，剩余量按 0 处理，不产生负数。
- 已发往模型供应商的调用允许完成；后续模型调用重新检查最新额度。
- 每日统计按北京时间日期归属，不依赖定时任务清零。
- 统计输入 Token + 输出 Token；工具调用、数据库查询和用户字符数不直接计费。
- 额度是服务端安全控制，前端展示不能绕过服务端判断。

## 方案比较与选择

### 方案一：数据库日账本 + 逐调用预留/结算（采用）

创建 Run 前和每次模型调用前预留额度，模型返回后按供应商 usage 结算并释放多余预留。该方案能在并发和多轮工具调用下阻止额度穿透，且适配当前 MySQL 原子限流模式。

### 方案二：结束时原子累加实际用量

只在 Run 结束后累加 usage，实现简单，但并发请求可以同时通过检查并超过当日成本上限，不满足线上成本保护目标。

### 方案三：Redis 窗口计数

使用 Redis 维护每日计数，性能较高，但会引入新的高可用、持久化和故障补偿依赖。现有服务以 MySQL 为主要持久化基础，暂不采用；多副本扩容时可再评估。

## 架构与数据模型

额度服务位于 `aisoftoj-ai`，因为 Run 创建、模型调用和 usage 结算均在 Python 服务内完成。Java 后端继续通过现有内部接口验证 JWT 和管理员角色，不参与扣费事务。

新增 Alembic 表：

### `ai_quota_config`

全局配置单例，至少包含：`id`、`daily_token_limit`、`updated_by_user_id`、`create_time`、`update_time`。默认额度为 30,000。更新使用数据库事务和行锁，审计日志记录管理员 ID、旧值、新值和时间，不记录凭证。

### `ai_daily_token_usage`

按 `user_id + usage_date` 唯一，至少包含：`user_id`、北京时间日期、`consumed_tokens`、`reserved_tokens`、`create_time`、`update_time`。不存在记录时在同一事务中创建。当天额度由当前 `ai_quota_config.daily_token_limit` 动态计算，不批量更新每个用户账本。

### `ai_token_reservations`

每次模型调用一条记录，关联 `run_id`、用户、北京时间日期和调用序号，包含 `reserved_tokens`、`prompt_tokens`、`completion_tokens`、`usage_source`、状态（`RESERVED`、`SETTLED`、`RELEASED`、`CHARGED_ESTIMATE`）和时间字段。`run_id + model_call_sequence` 唯一，保证重试或恢复不会重复计费。

现有 `ai_runs.prompt_tokens` 和 `completion_tokens` 改为记录一次 Run 内所有模型调用的累计值。

## 请求与结算流程

1. `POST /api/ai/threads/{thread_id}/runs` 校验身份、线程归属和幂等键。
2. 在创建用户消息和 Run 前只检查当天可用余额是否大于 0，不在此时预留整次 Run 上限；若余额为 0，返回 `429 AI_DAILY_TOKEN_QUOTA_EXCEEDED`，不保存消息、不启动模型任务。通过准入检查后，首轮模型调用仍必须执行下一步的精确预留，并可能因输入和最大输出所需空间超过剩余额度而终止。
3. 每次实际调用模型前，额度服务锁定当天账本，按“估算输入 Token × 1.10（向上取整）+ 本次模型请求的最大输出 Token”计算预留量；确认 `consumed + reserved + new_reserved <= current_limit` 后写入预留记录。安全余量通过配置项管理，默认 10%；最大输出 Token 必须由统一模型调用配置提供并实际传给供应商，额度服务与模型适配层读取同一值，不能各自维护不同上限。
4. 模型返回后读取 `usage_metadata` 中的输入、输出 Token，锁定预留和账本，将实际用量加入 `consumed_tokens`，并释放预留与实际用量之间的差额。
5. Agent 的每一轮“模型调用—工具调用—模型调用”都重复预留和结算；工具调用本身不扣 Token。
6. 供应商没有返回 usage 时，按本地估算值结算并标记 `usage_source=estimated`。
7. 实际 usage 超过预留时仍全额记账，并写告警日志。
8. Run 字段累计所有调用的输入和输出 Token；SSE 和既有 Run 状态契约保持兼容。

事务锁顺序固定为“配置 → 每日账本 → 预留记录”，避免死锁。所有时间在服务端使用 Asia/Shanghai 计算日期，API 时间字段使用带 `+08:00` 的 ISO 8601。

## 异常、恢复与并发

- 模型请求发出前失败：释放全部预留。
- 供应商明确失败且没有 usage：释放预留。
- 取消、超时或正常失败但已收到 usage：按真实 usage 结算。
- 服务崩溃或断网导致无法判断供应商是否计费：启动恢复时将未收敛预留按预留量标记为 `CHARGED_ESTIMATE`，防止通过断连反复获得调用；恢复流程必须幂等。
- 管理员调低额度不取消已发出的调用；后续调用读取新额度，额度不足则结束 Run 并保留已计费用量。
- 保留现有全局和单用户并发 Run 上限。本期不新增按分钟请求次数限制；若上线观测表明短请求滥用明显，再作为独立需求设计。
- 额度数据库或配置不可用时 fail closed，返回 `503 AI_QUOTA_UNAVAILABLE`，不调用模型。

## API 与后台

- `GET /api/ai/quota`：供前端在耗尽或 Run 结束后按需查询状态，不作为线上常驻余额展示。
- `GET /api/ai/admin/quota-config`：管理员查询当前全局额度、修改时间和修改人。
- `PATCH /api/ai/admin/quota-config`：管理员修改额度；本期固定接受 1,000–10,000,000 范围内的整数。额度不接受 0；紧急关闭 Agent 沿用现有可用性开关，不在本期新增开关能力。

错误契约：

- `429 AI_DAILY_TOKEN_QUOTA_EXCEEDED`：返回当前上限、已用、预留、剩余（最小为 0）和北京时间 `reset_at`。
- `503 AI_QUOTA_UNAVAILABLE`：不调用模型。

后台页面增加“AI 助手设置”区域，保存前提示“修改立即生效”，保存后重新读取服务端配置。普通用户界面只有在额度耗尽时显示“今日 AI 助手额度已用完，将于明日 00:00 恢复”，并禁用输入和发送；额度接口暂时失败时不伪造剩余数值。

## 监控与日志

指标至少包括模型输入/输出/总 Token、额度拒绝次数、估算结算次数、实际超预留次数、未收敛预留数和管理员修改次数。结构化日志关联 `run_id`、预留 ID、用户 ID 和 usage 来源，不记录用户消息、模型回复、JWT、Service Key 或 LLM Key。对 `CHARGED_ESTIMATE`、实际超预留和恢复失败告警。

## 测试与验收

- 默认值、后台权限、范围校验和立即生效。
- 北京时间跨日，服务运行在 UTC 时仍正确归属日期。
- 同用户并发不能超额，不同用户互不影响，幂等请求不重复预留。
- 多轮模型调用累计正确；真实 usage、缺失 usage 估算、失败释放、取消、超时和超预留均覆盖。
- 崩溃恢复按估算结算且重复恢复不重复扣费。
- 升额立即增加余额；降额低于已用量时阻止新调用但允许已发调用完成。
- 前端仅在耗尽时提示并禁用，额度查询失败不伪造余额。
- 既有 Run 幂等、SSE、取消、并发上限、单 Run Token 上限和服务重启收敛回归测试通过。
