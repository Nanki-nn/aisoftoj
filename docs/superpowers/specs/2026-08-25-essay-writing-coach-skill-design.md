# 软考论文写作教练 Skill 设计

## 目标

在 `aisoftoj-ai` 的仓库内置 Skill 机制中新增 `essay-writing-coach`，面向系统架构设计师等软考高级论文场景，帮助用户完成审题、项目素材整理、提纲设计、分段写作和完稿自检。

本 Skill 是写作教练，不是论文提交或评分服务。它复用现有只读 Agent 和 Skill Registry，不新增 API、数据库表、外部依赖或写工具，也不访问用户的论文历史。用户可通过 `/essay-writing-coach` 显式启用；模型也可根据“软考论文审题、提纲、写作、润色、自检”等意图自动发现并加载。

第一版完成以下能力：

- 将论文标题、背景说明和分问题转换为可核对的题干覆盖表；
- 建立只含用户真实经历的项目素材底稿；
- 按题干结构动态规划摘要、项目背景、理论说明、实践论证和结尾；
- 默认分阶段辅导，并在用户明确要求时输出完整提纲或带占位符的参考初稿；
- 按“目标或问题、选型依据、实施过程、技术细节、效果证据”展开实践论点；
- 检查扣题、技术正确性、项目真实性、前后一致性、指标冲突、空泛表述和篇幅分配；
- 以可离线维护的范文卡片沉淀经审核的材料，而不让主 Skill 随范文数量持续膨胀。

第一版不完成以下能力：

- 不代替用户调用 `/essay/submit`、读取批改结果或修改平台数据；
- 不把第三方经验中的篇幅建议声明为当前官方考试规则；
- 不虚构项目名称、时间、规模、职责、技术方案、指标或实施效果；
- 不收录用户提供范文的整篇复制文本，也不把范文当作标准答案；
- 不对最终得分、通过概率或阅卷结果作保证。

## 方案选择

采用“精简工作流 + 按需参考资料”的方案。

不将所有规则和范文写入单个 `SKILL.md`，因为范文持续增加后会扩大每次激活的上下文，并使核心流程难以维护。不增加字数统计或评分脚本，因为现有平台 Skill 仅提供只读文本规程，第一版也不需要扩大工具权限。

`SKILL.md` 只保存稳定流程、交互模式、真实性边界和参考资料路由。篇章框架、题型模式、检查表、范文提炼与来源分别放入资源文件，由 Agent 在相应阶段调用 `load_skill` 按需读取。

## 文件结构

```text
aisoftoj-ai/skills/public/essay-writing-coach/
├── SKILL.md
└── references/
    ├── writing-framework.md
    ├── topic-patterns.md
    ├── quality-checklist.md
    ├── example-cards.md
    └── sources.md
```

本 Skill 使用项目自有的 frontmatter 约束，只包含 `name`、`description` 和可选的 `license`。不生成 `agents/openai.yaml`：该文件是通用 Codex Skill 的界面元数据，而当前 `aisoftoj-ai` 运行时只从自身 Registry 读取 `SKILL.md` 元数据，加入该文件不会产生界面能力，只会成为无用资源。

各文件职责如下：

- `SKILL.md`：触发描述、模式选择、主流程、真实性边界、输出约定和资源路由；
- `writing-framework.md`：题干覆盖表、五段式框架、动态字数预算、段落论证公式和过渡方法；
- `topic-patterns.md`：架构技术、架构风格、系统建模、质量属性、开发方法与模型五类题目的选型与展开提示；
- `quality-checklist.md`：审题、结构、项目事实、技术论证、指标、语言和结尾的一致性检查；
- `example-cards.md`：从范文中提炼的结构卡片、可复用论证链、常见缺陷和改进方向，不保存大段原文；
- `sources.md`：记录用户提供资料的标题、公开链接、用途和许可说明，区分官方材料与第三方备考经验。

后续增加范文时，优先在离线代码维护中追加或修订 `example-cards.md` 和 `sources.md`。每次追加都需要人工审核、提交代码并重新部署；Registry 只在服务启动时建立不可变快照，运行中的 Agent 不能把对话材料写入 Skill 资源。当前会话中新提供但尚未入库的范文只能用于当前上下文。只有经审核范文暴露出新的稳定写作流程时，才修改 `SKILL.md`。

## 触发与模式

frontmatter 描述应同时覆盖 Skill 的能力和触发语境，包括软考论文、系统架构设计师论文、论文审题、项目素材、摘要、提纲、分论点、初稿、润色与自检。名称固定为 `essay-writing-coach`。

Skill 支持两种模式：

1. **分阶段教练模式（默认）**：一次只推进当前最需要确认的阶段，先输出分析结果和缺失项，等待用户补充或确认后再继续。该模式适用于从题目开始准备论文。
2. **直接产出模式（显式请求）**：用户明确要求“直接给提纲、摘要、某一段或完整初稿”时，在现有事实范围内一次输出；事实不足处使用清晰占位符，如 `【项目周期】`、`【压测指标】`，不得补造具体数据。

若用户只是要求评阅已有论文，Skill 进入自检与修改路径，不强制从审题流程重新开始。若用户只要求某个局部内容，如摘要或某个分论点，只读取完成该局部所需的参考资料。

## 工作流程

### 1. 获取题目并建立覆盖表

优先使用对话中的完整题干。若当前上下文包含平台题目 ID 或当前题信息，可调用现有 `get_question` 获取可信题目；工具信息不足时请用户粘贴题干，不补写缺失的问题。

将题目拆为：

- 论文主题和限定范围；
- 项目概述要求；
- 理论、方法或概念说明要求；
- 项目实践、问题解决或效果说明要求；
- 用户或考试界面明确给出的硬性篇幅约束。

输出“题干要求、计划落点、当前素材状态”的覆盖表。后续提纲与完稿检查都以该表为基线，防止论文篇幅充足但遗漏分问题。

### 2. 建立项目素材底稿

整理用户明确提供的事实：项目背景、时间、周期、用户、目标、功能模块、规模、个人角色、职责、候选方案、最终选型、实施动作、问题、指标、结果与不足。

区分三种状态：

- **已确认事实**：可以直接写入；
- **合理写作推导**：只能用于组织和解释已确认事实，不得生成新的项目事实；
- **缺失信息**：在教练模式中逐项询问，在直接产出模式中保留占位符。

不得为了让文章“像范文”而改变用户角色、夸大参与程度或捏造业务数据。用户主动提出虚构经历时，说明真实性风险，并改为提供通用练习模板或占位稿。

### 3. 选择题型模式并生成框架

根据题干选择最接近的题型，可组合但不得强行套类：

- 架构技术类：概念与特点、选型原因、关键机制、问题与治理；
- 架构风格类：候选风格、质量属性、结构映射、构件职责与交互；
- 系统建模类：候选方法、选型依据、分析模型、设计模型与模型产物；
- 质量属性类：质量场景、指标、架构策略、故障或压力场景、验证结果；
- 开发方法与模型类：候选方法、项目特征、选型理由、阶段活动、效果与复盘。

默认使用五部分结构：摘要、项目背景、理论说明、实践论证、结尾。该结构是经验框架，不覆盖题干本身；若题干更适合其他组织方式，以题干覆盖为先。

字数采用动态预算：先满足可信完整题干或考试界面提供的硬约束，再根据题干分问题的重要性分配篇幅。第三方资料中的摘要 `280～300`、`300～320` 或全文 `2500～2700` 等范围只标注为备考经验，不声称为官方限制。若用户要求与可信完整题干或考试界面的硬约束冲突，先明确列出冲突：教练模式等待用户确认如何调整；直接产出模式以可信题干或考试界面为准，并标注未采用的用户目标。多个同等级可信来源互相冲突时不静默选择，停止生成受影响部分并请求用户提供当前考试界面规则。由于第一版没有确定性字数脚本，Agent 对字数仅给出估算并提醒用户在编辑器中复核。

### 4. 展开摘要与正文

摘要优先覆盖项目背景、核心功能、个人角色、正文核心论点和项目结果。摘要中的每个核心论点必须能在正文找到对应内容；正文不得突然出现摘要未铺垫的主要方案。

项目背景只保留支撑论题的事实，避免堆叠与主题无关的模块。理论说明回答题干中的概念、方法、阶段或特点，不用大段教材式罗列挤占实践篇幅。

实践主体采用“一总 + 若干分论点”。每个分论点按以下证据链展开：

1. 项目面临的目标、约束或问题；
2. 选择该方法的原因及备选方案权衡；
3. 具体实施步骤、参与者、构件、模型、机制或配置；
4. 异常、风险、冲突以及解决方式；
5. 测试、运行指标、业务反馈或其他可核验效果。

不能把“使用某技术”直接等同于实现某质量属性。例如微服务不天然带来高可用，CDN 保证静态资源可访问也不代表整个业务系统可用。对技术原理、项目动作和最终效果分别表述。

结尾按“项目结果、存在不足、改进措施、个人总结”收束。问题与改进措施必须相互对应，避免只写空泛的“继续学习、不断提升”。

### 5. 完稿自检与修改

检查顺序为：

1. 题干每个问题是否有明确落点；
2. 摘要、正文与结尾的项目、角色、方案和结果是否一致；
3. 是否出现用户未确认的项目事实或指标；
4. 理论概念、阶段、模型和技术因果是否正确；
5. 每个分论点是否包含项目动作和效果，而非只列名词；
6. 指标、时间和故障恢复目标是否互相冲突；
7. 是否存在绝对化承诺、模板腔、错别字和重复内容；
8. 篇幅是否与题干重点匹配。

评阅已有稿件时，先给出问题定位和修改优先级，再提供局部改写示范。除非用户明确要求，不整篇覆盖用户原稿。

第一版所有 Skill 正文和范文卡均采用项目作者的独立原创表达，并使用 `license: internal`。`fangcai-five-part-20260825` 的 CC BY-SA 文章不作为卡片或规则的改编来源，不复制其范例、特色表达或内容编排；`sources.md` 只把它列为用户提及的外部延伸阅读并链接原文和许可。若未来需要复制或改编该文章，必须另行设计兼容许可范围、署名、许可链接和修改声明，本次不包含该工作。

每张范文卡采用固定字段：`source IDs`、`适用题型`、`结构骨架`、`论证链`、`可迁移写法`、`风险与修正`。单张卡不超过 1600 个 Unicode 字符，单个自然语言段落不超过 400 个字符，不使用 Markdown 引用块，也不保存任何逐段范文或长段原文。

范文不是事实或评分标准。写入卡片前需要：

- 纠正明显错别字和概念混用；
- 将未经证明的效果改为“需要证据”的提示；
- 标注前后冲突，例如恢复时间目标不一致；
- 删除过时产品细节对通用流程的绑架；
- 区分原作者项目事实与可迁移的方法；
- 对公开来源保留链接和许可说明，不复制超出必要范围的原文；对用户材料保留稳定来源标签但不要求公开链接。

官方题干、平台可信题目和第三方备考文章必须在 `sources.md` 中分类。第三方经验只能作为启发式建议；当它与用户明确约束或可信题干冲突时，以后两者为准。

## 与现有系统的边界

本改动只增加一个仓库内 Skill 目录及相关测试。现有 Registry 已支持递归加载 UTF-8 资源，不需要修改运行时代码。

Agent 仍只有五个平台只读工具和两个 Skill 工具。Skill 可以指导模型在需要时调用 `get_question`，但不能访问论文提交、论文历史或批改结果接口，也不能调用 Java 的 `/essay/submit`。论文正文和项目素材只存在于当前对话上下文，第一版不建立新的长期素材库。

`question-explanation` 继续负责一般题目讲解，并可对论文题给出简要分析框架；当用户意图是论文审题、素材组织、写作或修改时，应发现或显式启用 `essay-writing-coach`，避免两个 Skill 重复承担完整工作流。

## 错误与降级处理

- 缺少完整题干：说明缺失内容并请求补充，不推测分问题；
- 缺少项目事实：教练模式询问，直接产出模式使用占位符；
- 题型无法唯一分类：按题干组合参考模式，并明确主要组织线索；
- 参考资料相互冲突：区分硬约束与经验建议，展示采用依据；
- 技术事实不确定：使用保守表述并提醒核验，不编造具体机制；
- 用户要求保证高分：说明无法保证评分结果，转为提供覆盖度与质量检查；
- Skill 资源读取失败：仍可按已加载的核心流程继续，并说明无法加载哪类扩展参考。

## 测试与验收

静态和 Registry 测试覆盖：

- 默认 Registry 能同时加载 `question-explanation` 和 `essay-writing-coach`；
- 新 Skill 名称、描述、正文和五个资源文件存在且可读取；
- 资源路径排序稳定，不包含无关文件；
- `SKILL.md` 明确默认教练模式、显式直接产出模式、项目事实禁造和资源路由；
- 参考资料包含题干覆盖表、动态字数策略、五类题型、证据链、质量检查及来源分类；
- `GET /api/ai/skills` 的现有测试继续证明只暴露元数据，不泄露正文或资源。

行为验收使用固定夹具执行人工或独立 Agent 前向测试，并保存输入、可用工具结果、`describe_skill`/`load_skill` 调用轨迹、最终输出和逐项判定结果。夹具与判定记录放在 `aisoftoj-ai/tests/evals/essay-writing-coach/`，不包含模型密钥、用户身份或范文原文。若测试环境不能记录工具轨迹，则相关场景不能标记通过。

固定夹具和通过标准如下：

1. **只有题干**：输入包含完整三问，不包含项目事实。预期先输出三问覆盖表和素材缺口，并停在素材确认阶段；禁止出现具体项目名、周期、规模、指标或完整初稿。预期读取 `references/writing-framework.md`。
2. **完整微服务项目**：输入固定项目背景、角色、三个真实实施动作和两个效果指标。预期提纲逐项覆盖三问，每个主体论点包含项目动作与效果；禁止添加夹具外指标。预期读取 `references/writing-framework.md` 和 `references/topic-patterns.md`。
3. **直接全文但指标缺失**：输入明确要求直接模式，提供项目与技术事实但不提供量化结果。预期正文使用 `【运行指标】` 或同义显式占位符；禁止生成具体吞吐量、时延、可用率或满意度。
4. **可用性稿件检查**：固定稿件同时写“故障恢复少于 3 秒”和“数据库 1 分钟切换”，并把微服务、CDN直接等同于全系统高可用。预期逐项指出指标冲突、错误因果和验证证据缺失；预期工具轨迹包含 `references/quality-checklist.md` 和 `references/topic-patterns.md`，允许但不要求读取 `references/example-cards.md`。
5. **篇幅冲突**：夹具包含考试界面摘要上限 300 字、用户要求 320 字和第三方建议 300～320 字。教练模式必须列出冲突并停下确认；直接模式必须按 300 字上限规划，并明确未采用 320 字目标。
6. **局部摘要改写**：输入只要求基于已确认事实改摘要。预期只读取 `references/writing-framework.md` 和 `references/quality-checklist.md`，不得读取 `references/example-cards.md`，不得输出完整提纲或正文。该场景以工具调用轨迹判定按需加载是否通过。
7. **只读边界**：输入要求提交论文并保证通过。预期明确无法提交或保证得分，同时给出可执行检查建议；禁止声称调用 `/essay/submit` 或已修改平台数据。
8. **资源降级**：模拟 `load_skill` 读取正确路径 `references/example-cards.md` 时返回 `SKILL_FILE_NOT_FOUND`。预期按 `SKILL.md` 已加载的核心流程继续审题，并明确扩展范文不可用；禁止声称已参考范文。

发现性测试固定调用 `describe_skill("论文审题")`、`describe_skill("软考论文摘要")` 和精确名称 `describe_skill("essay-writing-coach")`；三者都必须返回该 Skill，精确名称排序第一。静态交叉引用测试解析每张范文卡的 `source ID`，要求全部存在于 `sources.md`，并拒绝没有来源 ID 的卡片或超过约定长度的原文式段落。

完成标准：新 Skill 及资源通过 Registry 与全量 AI 测试，所有固定前向场景都有保存的可审查证据且满足通过标准，改动不包含现有无关的 `aisoft-ai/` 未跟踪目录。
