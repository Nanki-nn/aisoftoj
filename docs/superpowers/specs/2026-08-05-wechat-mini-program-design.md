# 微信小程序学生端设计

## 背景

知构软考刷题平台当前以 React Web 前端和 Spring Boot 后端提供学习首页、试卷筛选、练题与考试、交卷结果、刷题历史、错题本、个人中心和论文练习。用户希望增加正式微信小程序版本，第一版只承载学生端核心刷题，不把管理员后台、AI 论文批改或其他运营功能搬入小程序。

现有后端已经提供试卷、练习会话、答题记录、历史和错题接口，`user` 表也预留了 `wx_open_id`，但尚无微信登录与邮箱账号绑定接口。现有 Web UI 依赖 React Router、Radix UI、Tailwind CSS、浏览器 DOM、`localStorage`、React Markdown 和 Web Crypto，不能直接编译为小程序。设计因此采用独立小程序工程，复用平台无关的类型和业务逻辑，重写小程序页面与运行时适配层。

## 目标

- 使用微信一键登录，新用户首次登录自动创建账号。
- 允许微信用户通过邮箱验证码绑定已有 Web 账号，完整保留原账号学习数据。
- 支持综合知识的单选、多选、判断和填空题。
- 支持案例分析长文本作答、草稿恢复、参考答案和解析对照。
- 支持练题模式、考试模式、暂停恢复、交卷、结果复盘、历史和错题本。
- 在弱网、切后台和进程被终止的情况下尽量避免未交卷答案丢失。
- 由服务端强制控制答案和解析的可见时机，而不是只在 UI 中隐藏。
- 对并发开始、乱序保存、迟到请求和重复交卷提供数据库级幂等与版本保护。
- 固定会话题目顺序、分值和判分策略，避免题库后续变化改写历史结果。
- 继续保护题目内容响应，不为小程序降级为成功明文响应。
- 保持现有 Web 邮箱登录、刷题和管理员功能兼容。

## 非目标

- 不实现论文练习、AI 批改或 AI 推荐。
- 不把管理员后台迁入小程序。
- 不实现排行榜、积分商城、好友系统、社交分享和消息订阅。
- 不缓存解密后的整套题目供长期离线使用。
- 不以 WebView 包装现有 Web 站点作为正式交付方案。
- 不为了共享代码而全面重构现有 Web 页面。
- 不在第一版支持多设备实时协同作答；发生版本冲突时显式提示并由用户选择最新答案。

## 方案选择

候选方案包括 Taro + React、原生微信小程序和 WebView 包装。

- Taro + React 可以沿用团队现有 React 与 TypeScript 经验，复用类型、DTO 映射和部分会话逻辑，同时让页面使用微信小程序原生能力。
- 原生 WXML + TypeScript 的运行时依赖最少，但现有 React 状态逻辑和页面基本都要重写，预计比 Taro 多 10～15 人日。
- WebView 初期工作量最小，但无法良好承载微信登录、原生导航、后台恢复和正式小程序体验。

第一版选择 **Taro + React 独立工程**。现有 Radix UI、Shadcn 组件、Tailwind 类和 React Router 不作为跨端依赖；小程序页面使用 Taro/微信基础组件和面向小程序的样式。

## 范围与页面

### TabBar

1. **首页**：考试倒计时、继续上次练习、最近学习数据和试卷快捷入口。
2. **试卷**：按科目、年份和试卷类型筛选，展示进度、开始和继续练习入口。
3. **错题**：展示错题、错误次数和所属试卷，支持定位到原会话中的题目。
4. **我的**：学习统计、刷题历史、邮箱绑定、退出登录和隐私入口。

### 普通页面

- 微信登录与登录恢复。
- 刷题配置：练题模式或考试模式。
- 答题会话。
- 答题卡抽屉。
- 交卷确认。
- 结果与逐题复盘。
- 刷题历史。
- 邮箱验证码绑定。

### 答题交互

- 顶部固定显示题号、答题进度和计时。
- 底部固定显示上一题、下一题和答题卡入口。
- 练题模式允许确认单题后查看答案和解析；考试模式在交卷前隐藏答案。
- 客观题使用小程序选择控件；案例题使用大文本输入、字数提示和保存状态。
- 答题卡区分当前题、未答、已答和已标记状态。
- 交卷前展示未答题数量并要求二次确认。
- 结果页把客观题得分与案例题完成情况分开呈现。

## 仓库与模块边界

建议结构：

```text
packages/core/
  src/types/            平台无关的用户、试卷、题目和会话类型
  src/mappers/          后端 DTO 到领域模型的纯映射
  src/session/          答案格式、完成度和客观题判分纯函数

aisoftoj-mini/
  src/pages/            小程序页面
  src/features/auth/    微信登录、会话恢复和邮箱绑定
  src/features/papers/  试卷目录、筛选和开始会话
  src/features/session/ 答题状态、草稿、同步和提交
  src/features/history/ 历史与复盘
  src/features/wrong/   错题列表与原题定位
  src/services/         小程序 API 客户端
  src/adapters/         storage、crypto、rich-text 运行时适配
  src/components/       题目、选项、答题卡和状态组件
```

共享包只接收无 DOM、无路由、无存储和无网络副作用的代码。Web 可以逐步改用共享包，但小程序首版不以完成 Web 全面迁移为前提。

仓库根目录建立唯一 JavaScript workspace，固定使用 pnpm 和一个根锁文件管理 `packages/core`、`aisoftoj-front` 与 `aisoftoj-mini`。实现前先核对当前未提交的 `aisoftoj-front/pnpm-workspace.yaml` 和锁文件，不能覆盖用户已有配置；CI 分别执行共享包测试、Web 测试/构建和小程序构建。禁止同时维护 npm 与 pnpm 两套会漂移的锁文件。

答题会话拆分为：

- `SessionController`：当前题、题目顺序、计时、暂停、恢复和提交。
- `AnswerStore`：答案、标记状态、待同步队列和本地草稿。
- `QuestionRenderer`：按题型选择对应输入组件。
- `QuestionContent`：把题干和解析转换为小程序安全富文本。
- `AnswerSheet`：答题进度和快速跳题。
- `SessionResult`：客观题统计和案例答案对照。

小程序状态优先使用局部 React reducer 和少量上下文，不为首版引入覆盖全应用的大型状态框架。

## 微信登录与账号绑定

### 配置与安全边界

- AppID 和 AppSecret 只保存在后端环境变量中。
- 小程序只向后端提交 `wx.login` 返回的临时 code，不接收或持久化微信 `session_key`。
- 后端用 code 换取 OpenID，禁止把 code、AppSecret、session key 或完整微信响应写入日志。
- 换取 OpenID 前按 IP 限流，换取成功后再按 OpenID 限流；无效或重复 code 返回统一认证错误。
- 登录不强制索取微信头像或昵称；新用户使用安全默认昵称，避免把非必要授权放进核心路径。
- 小程序登录和绑定只允许 `USER` 角色。数据库中即使存在错误绑定了 OpenID 的 `ADMIN`，微信登录也必须拒绝签发管理员 JWT。
- 所有会修改练习数据的事务先锁定并重新校验当前用户行、`token_version`、启用状态和删除状态。这样账号合并等待中的旧请求只能在合并前完成并被迁移，或在合并后失败，不能把数据继续写回临时账号。

### 接口

#### `POST /auth/wechat/login`

请求：

```json
{ "code": "wx-login-code" }
```

OpenID 已存在且对应启用的 `USER` 时登录；不存在时创建邮箱为空、角色为 `USER` 的微信用户。OpenID 指向管理员、删除或禁用账号时返回统一认证错误。成功响应继续使用现有 `AuthResponse`，由项目 JWT 保护后续 API。

#### `POST /auth/email/bind/code`

要求当前 JWT 对应“邮箱为空、角色为 `USER`、持有 OpenID”的临时微信用户。请求：

```json
{ "email": "user@example.com" }
```

邮箱验证码服务新增独立的 `BIND_EMAIL` 场景；验证码不得跨注册、登录、重置和绑定场景使用。投递规则为：

- 数据库完全不存在该规范邮箱：发送可消费验证码，成功绑定时设置 `email_verified_at`。
- 存在启用、未删除、已验证的普通 `USER`：发送可消费验证码，用于证明用户拥有待合并账号。
- 存在 `ADMIN`、禁用、软删除或未验证账号：返回与正常请求相同的受理响应，但写入不可消费的 `SUPPRESSED` 记录且不发信，避免枚举账号状态。

发送端继续执行邮箱、IP 和当前用户维度的数据库原子限流。软删除账号仍占用邮箱唯一键，因此不属于“未注册邮箱”，不得自动复用。

#### `POST /auth/email/bind`

请求：

```json
{ "email": "user@example.com", "code": "123456" }
```

只有邮箱验证码消费成功后才执行绑定。成功返回新的 `AuthResponse`；如果发生账号合并，小程序必须立即替换 JWT 和用户资料。客户端不得在收到 `401` 后自动重放绑定请求。

### 绑定与合并规则

- 当前账号必须是邮箱为空、角色为 `USER`、启用且未删除的微信临时账号。
- 邮箱尚未存在任何记录：在消费验证码的同一事务内绑定邮箱并设置验证时间。
- 邮箱已有启用、未删除、已验证的普通 `USER` 且未绑定 OpenID：以原邮箱账号作为主账号并迁移临时账号学习数据。
- 邮箱账号已经绑定同一 OpenID：重新微信登录后按幂等成功处理。
- 邮箱账号已经绑定其他 OpenID：返回 `409`，禁止覆盖或自动解绑。
- `ADMIN`、禁用、软删除或未验证账号不得作为自动合并目标，绑定阶段统一返回不可完成的认证错误。
- 已经绑定邮箱的微信账号不能改绑其他邮箱；绑定同一邮箱只允许在重新微信登录后返回当前状态。

合并事务按用户 ID 固定顺序锁定两条用户记录，重新校验角色、状态、邮箱和 OpenID 后执行：

1. 在修改任何用户数据前锁定并验证仍为 `ACTIVE` 的 `BIND_EMAIL` 验证码；验证码状态更新与后续迁移在同一事务提交。随后锁定临时账号涉及的活动会话和错题行，阻止并发写入穿过迁移窗口。
2. 迁移已完成会话。不存在活动冲突时直接迁移活动会话。
3. 两个账号存在同一 `paper_id + exam_mode` 活动会话时，以邮箱主账号会话为胜者；仅把临时会话中“主会话为空”的答案复制到主会话，双方都有不同非空答案时保留主账号答案。临时会话标记为 `MERGED` 并记录 `merged_into_session_id`，不计入历史统计。
4. 错题以 `(user_id, question_id, active_marker)` 为唯一业务键原子合并：累计 `error_count`，`last_wrong_time` 取较晚值，重要级别按 `low < medium < high < must` 取较高值，其他展示字段在更新时间相同的情况下以较小记录 ID 为确定性胜者。
5. 先把临时账号的 `wx_open_id` 置为 `NULL`，再把相同 OpenID 写入主账号；该顺序满足现有 `wx_open_id` 唯一约束。
6. 递增临时账号 `token_version` 并软删除临时账号，使旧 JWT 失效。
7. 消费 `BIND_EMAIL` 验证码并签发主账号新 JWT。

任一步骤失败必须整体回滚。论文提交不在小程序首版迁移范围内；原邮箱账号已有论文数据会继续保留在主账号下。

如果服务端已完成合并但响应丢失，旧 JWT 会失效；客户端重新执行 `wx.login` 后，OpenID 已指向主账号，可直接拿到主账号新 JWT 和已绑定邮箱状态。客户端不复用已消费验证码，也不自动重放合并请求。

## 会话与答题数据流

### 数据库约束与会话快照

MySQL 5.7 通过生成列和唯一索引强制以下约束：

- `practice_session.active_marker = IF(status = 0 AND is_deleted = 0, 1, NULL)`，唯一键为 `(user_id, paper_id, exam_mode, active_marker)`；同一用户、试卷和模式最多一个活动会话，完成或合并会话因 `NULL` 可保留多条。
- `practice_session_question_record` 增加唯一键 `(session_id, question_id)`。
- `user_wrong_question_stat.active_marker = IF(is_deleted = 0, 1, NULL)`，非空 `question_id` 使用 `(user_id, question_id, active_marker)` 唯一键并通过原子 upsert 累计。

`paper_question_relation` 增加非空 `order_num`，现有关系按 relation ID 顺序回填。会话题目记录增加 `paper_question_relation_id`、`question_order`、`score_snapshot` 和 `grading_strategy_snapshot`。开始会话时按 `paper_question_relation.order_num, id` 固定顺序和分值；后续详情、答题卡与交卷只读取这批记录，不重新枚举当前试卷关系。

发布后的试卷、关系、题目正文、选项、答案、解析和判分策略视为不可变。管理员修改已发布或已有会话引用的内容时必须复制出新试卷版本，旧版本继续服务历史会话。`paper.question_total` 是关系数量的受约束缓存：发布和迁移前重算，发现声明值与有效关系数量不同则阻止发布，不允许静默截断或使用错误分母。

### 启动与恢复

1. 启动时读取小程序本地 JWT。
2. 有 JWT 时调用 `/auth/me`；合法则恢复用户，无效则清理本地认证并执行一次微信登录。
3. 微信登录失败时显示可重试错误，不进入需要用户身份的页面。
4. 首页调用新增 `GET /session/active`，按 `update_time DESC, id DESC` 返回所有活动会话的 sessionId、paperId、mode、进度和更新时间；不再从 `/paper/list` 的单个任意 `doingSessionId` 猜测模式。

### 开始会话

- 用户选择试卷和模式后调用现有 `/session/start`。
- 开始事务先锁定并校验用户，再尝试创建活动会话。活动唯一索引发生竞争时捕获重复键并重新查询既有活动会话，保证并发请求只得到一条会话。
- 查询必须包含 `is_deleted = 0`，初始化题目记录使用 `(session_id, question_id)` 唯一键避免重复。
- 小程序收到加密会话数据后初始化 `SessionController` 和版本化本地草稿。

### 版本化答案保存

题目记录增加：

- `answer_revision bigint unsigned NOT NULL DEFAULT 0`。
- `last_mutation_id varchar(64) NULL`。
- `confirmed_at datetime NULL`，表示练题模式已经确认并解锁答案；单纯保存草稿不再复用 `is_submitted` 表达确认。

`PATCH /practice/session/question/record/{recordId}` 请求为：

```json
{
  "userAnswer": "A",
  "spendTime": 12,
  "expectedRevision": 3,
  "mutationId": "uuid",
  "confirm": false
}
```

服务端在同一事务内锁定用户、会话和题目记录，只允许修改 `DOING` 会话。相同 `mutationId` 重试直接返回当前记录；`expectedRevision` 不匹配时返回 `409` 和当前服务端答案/版本，不执行覆盖；成功写入后 revision 加一。练题模式 `confirm=true` 后按快照策略判分并设置 `confirmed_at`，确认后的记录不可再修改。考试模式拒绝单题确认。

`is_submitted` 只在练题确认或整卷交卷时设为 true；普通草稿保存即使已有非空答案也保持 false。

- 客观题选择和案例文本输入先更新内存状态，再立即写入本地答案草稿。
- 客观题变更可以立即同步；案例文本采用短防抖同步，降低频繁请求。
- 每道题草稿记录答案、服务端 revision、mutationId 和 `pending` 状态。后端确认成功后才清除 `pending`。
- 切后台时尽力刷新待同步队列并调用暂停接口；由于小程序生命周期不保证异步请求完成，本地草稿始终是最后一道保护。
- 当前内存中已解密的题目可以在短暂断网时继续作答，但不得把整套解密题目长期写入本地存储。

### 冲突与重新进入

重新获取会话时先以服务器答题记录为基础，再只覆盖本地 `pending` 草稿。若 pending 草稿的 expectedRevision 已落后，客户端显示冲突，不自动覆盖服务器值；用户可以保留服务器值，或基于最新 revision 明确重新提交本地草稿。已经确认同步的旧本地答案不能覆盖服务器新值。当前题号和标记状态可以从本地恢复，但不影响服务器答案真值。

### 交卷

1. 检查未答题并二次确认，生成稳定 `submissionId`。
2. 将 `submissionId` 和当前完整答案集合提交到 `/session/submit/{sessionId}`，不依赖单题同步是否已经全部完成。
3. 服务端事务先锁定用户与会话，再锁定全部题目记录。第一份拿到锁的提交以请求中的完整答案为最终值，计算成绩和错题后把会话置为 `FINISHED` 并持久化 `submission_id`。
4. 会话已经完成时，任何重复提交都不再修改答案、分数或错题，只返回持久化结果；等待中的迟到 PATCH 在拿到会话锁后因状态不是 `DOING` 被拒绝。
5. 服务端直接返回 `SessionResultDTO`；响应丢失时客户端可通过 `GET /session/{sessionId}/result` 恢复相同结果。
6. 只有服务端确认成功或结果接口确认已经完成后才清除本地草稿并进入结果页。

`SessionResultDTO` 至少包含 score、totalScore、answeredCount、gradableCount、manualCount、gradingAvailable、完成时间和逐题结果，能够在冷启动后独立重建纯客观、混合或纯案例结果页。

### 计时

- 界面计时以服务端 `startTime` 和暂停状态计算，不把前端 `setInterval` 次数当作真实时间。
- 切后台时记录本地显示状态并尽力暂停；返回时重新读取服务端会话以校准。
- 考试模式交卷前由服务端省略答案、解析和正确性；练题模式只对已经 `confirmed_at` 的题目返回这些字段。确认状态随答题记录恢复。

### 服务端答案可见性

- `POST /session/start` 和 `GET /session/{id}` 根据会话所有者、模式、状态和 `confirmed_at` 构造专用 DTO。
- 进行中的考试会话不返回任何标准答案、解析或 `isCorrect`；完成后只能通过结果接口读取。
- 进行中的练题会话只为已确认题目返回答案、解析和正确性；未确认题目保持裁剪。
- 普通用户调用 `/question/{id}?withAnswer=true` 必须被拒绝；`withAnswer=true` 只允许管理员。用户复盘统一通过自己拥有的会话结果接口。
- `/paper/detail/{paperId}` 对普通用户永不返回答案和解析，管理能力使用管理员接口。
- Web 端必须和小程序一起迁移到确认端点与裁剪 DTO；应用层加密只隐藏网络明文，不能代替这些授权规则。
- 错题统计增加 `last_session_id`，每次原子 upsert 时指向最近一次产生该错题的已完成会话；错题页“查看原题”使用这个会话和 questionId，不再临时猜测任意历史会话。

## 题型判分与案例分析

`question` 增加明确的 `grading_strategy`：

- `EXACT_CHOICE`：单选和判断，去首尾空白并统一选项键大小写后比较。
- `SET_CHOICE`：多选，按逗号拆分、去重、排序后比较。
- `ORDERED_BLANKS`：填空，按现有 `||` 分隔多个空，逐项去首尾空白并做 Unicode NFKC 规范化后按顺序比较；首版不支持同一空的多个备选答案。
- `MANUAL`：案例和论文，不自动判分。

迁移按题型回填策略，并在发布前校验答案格式；格式不合法的填空题阻止发布，不能静默错误判分。成绩使用 `paper_question_relation.score` 的快照，不再固定每题 1 分。

当前 `practice_session_question_record.user_answer` 为 `varchar(255)`，无法保存案例长文本。迁移为允许 `NULL` 的 `TEXT` 且不设置默认值；未作答记录显式写 `NULL`。服务层使用 `String.codePointCount` 限制最多 10,000 个 Unicode code point，单题 PATCH 和交卷嵌套 answers 都执行相同校验，超限统一返回 `422`。

判分逻辑由单题确认与整卷提交共用同一 `GradingService`：

- 案例分析不进行字符串相等判分，`is_correct` 保持 `NULL`。
- 案例题不增加错题统计。
- `score` 和 `total_score` 只统计非 `MANUAL` 题目的关系分值。
- 纯案例试卷结果显示“本试卷不自动判分”，而不是 `0/0` 或 `0 分`。
- `answered_count` 仍包含已经填写的案例题。

结果页对案例题显示用户答案、参考答案和解析，不显示正确或错误标记。

## 题目内容加密适配

现有题目响应使用 RSA-OAEP-256 包装逐响应 AES-256-GCM 密钥。小程序继续使用同一协议和失败关闭语义：

- `MiniProgramContentCrypto` 负责生成临时 RSA 密钥、导出公钥头和解密信封。
- 小程序启动或冷启动生成新的临时密钥；私钥只驻留内存，不写入 storage。
- 成功响应缺少加密标记、信封字段异常、RSA 解包失败或 GCM 校验失败时拒绝内容，不回退为成功明文。
- 普通 4xx/5xx 错误继续按统一 JSON 错误处理。
- 首个技术验证阶段必须在真实微信开发者工具和至少一台真机验证所选密码库的 RSA-OAEP、AES-GCM、随机数质量、包体积和 Java 互操作。
- 如果候选库不能满足协议与包体要求，允许替换小程序密码库实现，但不允许静默修改协议或取消加密；协议变化必须单独评审并提供 Java/小程序互操作测试。

共享 API DTO 映射位于 `packages/core`，网络、请求头、JWT storage 和密码实现由 Web 与小程序各自适配。

## 富文本适配

- `QuestionContent` 接收已经解密的题干或解析，输出小程序可渲染的安全节点。
- 只允许明确的文本、段落、列表、表格、代码、强调、换行和图片标签/节点。
- 删除脚本、样式、事件属性、JavaScript URL 和未知危险节点。
- 图片必须使用 HTTPS 且来源于允许域名；加载失败显示占位和重试入口。
- 题目正文、选项、参考答案和解析使用同一套渲染规则，避免各页面产生不一致解释。
- 首版不提供富文本编辑；案例答案使用纯文本输入。

## 错误处理与离线行为

- API 层统一映射 HTTP 状态和业务 `code`，页面不直接解析底层响应。
- `401` 时最多自动执行一次微信重新登录。只有 GET、数据库唯一约束保护的 start、带 mutationId/revision 的 PATCH 和已完成结果不可变的 submit 可以安全重试；邮箱绑定等认证变更不得自动重放。
- `409` 用于账号已绑定其他 OpenID、答案 revision 冲突和已确认题目再次修改，响应只包含解决冲突所需的当前资源状态，不泄露其他账号信息。
- `422` 用于超长案例答案或题型数据校验失败；`413` 保留给超过题目加密响应总大小上限的请求结果。
- 开始会话和交卷显示不可重复点击的进行中状态。
- 短暂断网时，已打开会话可以继续写本地答案；开始新会话、加载未缓存题目和交卷必须等待网络恢复。
- 冷启动离线时不展示长期缓存的解密题目，只提示联网恢复会话。
- 同步失败保留 `pending` 状态并指数退避重试；用户始终能看到“已保存到本地 / 正在同步 / 同步失败”状态。

## 数据迁移与发布前置

- 生产 Flyway 当前最新版本为 V4，本功能使用 `aisoftoj-backend/src/main/resources/db/migration/V5__wechat_mini_program_session_foundation.sql`；如果合入前已经存在新的 V5，则顺延到下一个可用版本，禁止复用版本号。
- 根目录 `db_schema.sql` 同步更新全量初始化结构，但它不能代替生产 Flyway。
- 迁移前预检活动会话重复、同会话题目记录重复、同用户题目错题重复、题目判分策略格式、`paper.question_total` 与有效关系数量差异。配套修复工具先 dry-run：重复活动会话按 `update_time DESC, id DESC` 选胜者，用较新 loser 的非空答案只填充 winner 空答案并把 loser 标记 `MERGED`；同一题存在冲突非空答案则停止等待人工选择；错题按本文 canonical key 合并；题目总数重算；关系顺序按 relation ID 回填。dry-run 无未决冲突后才显式 apply，再执行 Flyway。禁止随机挑选数据继续。
- 迁移采用 expand/contract：先增加可空字段、回填并验证，再建立生成列/唯一索引，最后发布依赖新合同的后端和前端。
- 在 MySQL 5.7 真实实例上执行从 V4 升级、重复启动、备份恢复和旧 Web 兼容测试。
- 验收环境必须至少有一份已发布的综合试卷和一份已发布的案例试卷；仓库测试夹具提供最小案例数据，生产题库内容仍走现有导入流程。

## 验收标准

- 新用户能通过微信完成登录、开始试卷、作答、交卷和复盘。
- 已有用户绑定邮箱后，原 Web 历史与错题完整保留并可在小程序查看。
- 杀掉小程序再打开，未交卷答案能够恢复，已同步旧缓存不会覆盖服务器新答案。
- 案例题长文本可以保存、恢复和查看参考答案，不进入客观题得分或错题统计。
- 重复开始、保存和交卷不会产生重复会话、重复提交或重复错题统计。
- 进行中考试无法从任何普通用户接口提前读取答案或解析。
- 已发布试卷的历史会话题序、分值和结果不会因后台后续编辑发生变化。
- 题目加密失败时不展示成功明文。
- 管理员、AI 论文、排行榜等非目标功能不进入首版。

## 交付阶段与估算

### 阶段一：合同加固与风险验证，7～10 人日

- 完成数据库预检、会话/判分/答案可见性合同和实施计划。
- 建立 Taro + React 工程和基础导航。
- 建立共享 core、请求和 storage 适配。
- 验证小程序题目加密互操作和富文本渲染。
- 增加微信登录最小后端链路。

阶段出口是“微信登录 -> 试卷列表 -> 打开一套经过服务端裁剪的真实加密题目”的真机纵切可运行。仅用于验证技术风险，不宣称具备生产数据一致性。

### 阶段二：会话安全与判分基础，14～20 人日

- Flyway V5、数据预检、唯一约束和会话题目快照。
- revision/mutationId 保存、练题确认、服务端答案裁剪和不可变交卷结果。
- 案例长文本、判分策略、关系分值和错题原子 upsert。
- 并发、迁移和 Web 合同回归测试。

### 阶段三：微信身份与账号合并，8～12 人日

- 微信 code 登录、配置、限流和错误处理。
- BIND_EMAIL 验证码投递规则。
- USER-only 账号合并、活动会话冲突、OpenID 转移和响应丢失恢复。

### 阶段四：核心小程序页面，15～22 人日

- 首页、试卷、配置、答题会话和答题卡。
- 交卷结果、逐题复盘、历史、错题和个人中心。
- 案例草稿、revision 冲突、同步状态、后台暂停和恢复。

### 阶段五：回归与发布，8～12 人日

- 弱网、异常、真机和兼容性修正。
- Web 回归、生产配置、隐私说明和发布检查。
- 小程序提审与审核问题修正。

首个技术纵切预计 **12～18 人日**；达到本文验收标准的生产首版预计 **52～76 人日**。单人顺序开发约 10～15 周；前后端两人并行约 6～9 周。微信平台审核等待时间不计入开发人日。

相比最初 30～45 人日估算，上调来自现有后端必须补齐的数据库级活动会话唯一性、乱序保存版本协议、不可变交卷结果、服务端答案裁剪、稳定题序/分值和安全账号合并。这些不是新增产品功能，而是“微信端可恢复、可重试、考试不泄题”的上线前提。

## 发布与回滚

- 小程序后端能力先以兼容新增接口发布，不改变 Web 现有登录接口。
- 数据库迁移先扩展、回填并校验字段，再建立唯一约束，最后发布依赖新合同的后端和客户端。
- 微信登录和邮箱绑定使用独立配置开关；异常时可以关闭新登录入口，不影响 Web 用户。
- 会话、答案裁剪和案例判分修正属于共享后端行为，上线前必须同步升级 Web 并用真实综合与案例试卷回归。
- 小程序首版发布失败时下架或回退小程序版本，后端新增接口可以保留；不得回滚已经完成的账号合并。

## 已批准决策

- 第一版只做学生端核心刷题。
- 使用 Taro + React 独立小程序工程。
- 使用微信一键登录，并允许绑定已有邮箱账号。
- 支持综合知识客观题和案例分析，不支持论文与 AI 批改。
- 保留练题模式与考试模式。
- 管理员后台继续使用 Web。
- 案例题保存长文本，但不自动判分且不进入错题统计。
- 考试答案隐藏由服务端强制，练题答案只在单题确认后返回。
- 会话写入使用 revision/mutationId，交卷后结果不可再被 PATCH 修改。
- 题目顺序、分值和判分策略在会话创建时固定。
- 题目内容加密不为小程序降级为成功明文。
- 不增加非目标产品功能；按上线级一致性要求重新估算为 52～76 人日。
